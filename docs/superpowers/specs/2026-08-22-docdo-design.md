## 1. 한 문장

**어르신이 우편물을 사진 한 장 찍으면, 무엇이고 뭘 해야 하는지 큰 글씨와 목소리로 알려주고 —
멀리 있는 자녀에게는 처리에 필요한 모든 것을 준비해서 넘기는 문서 에이전트.**

이건 어르신용 앱이 아니다. **자녀를 대신해 읽고, 찾고, 준비하는 에이전트**다.
어르신은 그 에이전트의 눈이 되어 사진을 찍을 뿐이다.

---

## 2. 문제

어르신 우편함에는 건강보험료·지방세·전기·가스 고지서, 연금·복지 신청 안내문, 체납 독촉장,
보험 권유 DM, 광고, 그리고 공공기관을 사칭한 가짜 고지서가 뒤섞여 온다.

문서를 받은 사람은 스스로 네 가지를 판단해야 한다.

1. 이게 무슨 문서인가
2. 나에게 중요한가
3. 언제까지 무엇을 해야 하는가
4. 어떻게 처리하는가

**문해력이 낮은 고령자에게는 이 판단 자체가 불가능하다.** 그 결과 납부기한을 놓쳐 가산금을 물고,
신청만 하면 받는 복지를 접수기간 안에 못 챙기고, 사칭 고지서의 가상계좌로 돈을 보낸다.

보호자는 멀리 있어 대신 볼 수 없고, 전화로 "뭐라고 써 있어?"를 물어야 겨우 알며,
곁에 사람이 없는 날에는 확인할 방법조차 없다.

### 근거 — **발표 전 출처 링크를 반드시 채운다**

| 지표 | 값 | 출처 상태 |
|---|---|---|
| 기초연금 수급 자격이 있으나 미신청한 노인 | 41만 명 | 2024 국정감사 — **원문 링크 확보 필요** |
| 지방세 기한 경과 가산세 | 3% + 월 0.66% (최대 60개월) | **지방세법 조문 링크 확보 필요** |
| 공공기관 사칭 스미싱 증가 | 2년 새 70배 (1.8만 → 약 125만 건) | **출처 확보 필요** |
| 보이스피싱 피해자 중 60대 이상 | 30.6% | **출처 확보 필요** |
| 경북 고령인구 비율 | 26.1% (전국 2위), 초고령 시군구 19곳 | 대회 개최지 |

> **출처가 확보된 것만 발표에 쓴다.** 심사위원이 Upstage 엔지니어라 숫자를 흘려듣지 않는다.
> 검증 못 한 숫자는 아예 빼는 편이 낫다. **발표에는 검증된 것 하나만 쓴다.**

### 기존 서비스와의 차이 — **절대 표현 금지**

국민비서 구삐, 토스 내문서함, 웰로, 복지멤버십은 **발송 기관이 전자고지에 가입해야 작동한다.**
DocDo는 **이미 손에 들린 종이에서 시작한다.** 발송 기관의 협조가 필요 없다.

> ~~"기존 서비스는 전부 push 모델"~~ / ~~"국내외 선례 없음"~~ 같은 절대 표현은 쓰지 않는다.
> 반례 하나만 나와도 무너지고, Q&A에서 그걸 아는 사람이 앉아 있을 수 있다.
> **"우리가 확인한 주요 서비스는 ~ 방식이고, 우리는 ~ 방식이다"**로 말한다.

## 3. 사용자 — 그리고 **누가 무엇을 할 수 있는가**

| | **어르신** | **자녀** |
|---|---|---|
| 상황 | 문해력·디지털 역량 낮음. 글씨가 커도 못 읽을 수 있음 | 멀리 살고 바쁨. 부모 우편물을 볼 방법이 없음 |
| **할 수 있는 것** | **사진 찍기. 듣기.** | 판단, 납부, 신청, 전화, 방문 |
| **할 수 없는 것** | 납부 화면 조작, 온라인 신청, 서류 준비 | 부모 우편물을 직접 보는 것 |

**이 표가 이 설계의 뿌리다.** 정보를 받는 사람과 행동할 수 있는 사람이 다르다.
어르신에게 "기초연금 받으실 수 있어요"를 보여줘 봐야 신청할 수 없다.
**알려주기만 하고 끝나는 정보는 무력감만 준다.**

### 범위 밖 (의도적 제외)

- 요양보호사·복지기관 — 권한·동의·다인 관리가 다른 B2B 제품
- 다자녀 공동 관리 — 가구당 자녀 1명 고정
- 자녀가 없거나 응답하지 않는 어르신 — 이 제품이 풀 수 있는 문제가 아니다

## 4. 안전 원칙 — 다른 모든 결정보다 우선한다

### 원칙 1 — 어르신 화면에는 금전 거래로 이어지는 경로를 두지 않는다

계좌번호도, 납부 버튼도, 결제 화면 링크도 없다.
어르신에게 주는 것은 **이해 · 안심 · 위험 경고 · 검증된 공식 전화번호**뿐이다.

> 사칭 피해를 막겠다는 서비스가 어르신을 결제 화면으로 밀어넣으면 자가당착이다.

### 원칙 2 — 확신하지 못한 값은 읽지 않는다

Extract가 `low`를 준 필드나 결손 필드는 **음성으로도 화면으로도 숫자를 말하지 않는다.**

> ❌ (금액이 `low`인데) "3만 2천원입니다" → 자녀가 나중에 검토
> ✅ "금액을 정확히 읽지 못해서 자녀분께 확인을 부탁드렸어요"

잘못 읽힌 숫자를 먼저 말한 뒤 검토하는 구조는 검토가 아니다.

### 원칙 3 — 지시하지 않는다. 사실만 전달한다

우리는 이미 냈는지, 자동이체인지, 연체 조정이 있는지 모른다.

> ❌ "8월 30일까지 3만 2천원만 내시면 됩니다"
> ✅ "문서에 적힌 청구 금액은 3만 2천 원, 납부기한은 8월 30일입니다"

### 원칙 4 — 확률적 판단으로 폐기를 지시하지 않는다

> ❌ "광고입니다. 버리셔도 됩니다"
> ✅ "광고로 보여요. 버리시기 전에 자녀분께 한 번 확인해 주세요"

오분류 한 번이 복지 안내문을 버리게 만든다. **광고도 자녀 목록에는 남긴다** (알림만 보내지 않는다).

### 원칙 5 — 문서에서 추출한 연락처·링크는 실행 경로가 되지 못한다

전화 걸기·링크 열기는 **`issuer_registry.json`에 등록된 공식 값으로만** 가능하다.
문서의 번호를 그대로 걸게 하면 검증 계층을 스스로 우회시키는 것이다.

## 5. 사용자 흐름

### 5.1 가입 — 역할 분기

```
앱 첫 실행
   "누구신가요?"
   ├─ [부모님을 도와드려요]  → 이름 입력 → 가구 생성 → QR 표시
   └─ [어르신이에요]        → 카메라로 QR 찍기 → 연결 완료
```

어르신이 이 앱에서 하는 동작은 오직 **"찍기"** 하나여야 한다. 가입도 찍기, 우편물도 찍기.

**연결 토큰 요건:** 128비트 난수 · 1회성 · 만료(10분) · 서버에는 해시만 저장 · 역할 고정.
원문을 DB에 두면 탈취 시 재사용된다.

> **데모에서는 가입 과정을 시연하지 않는다.** 5분에 넣을 자리가 없다.
> 이미 연결된 가구로 시작한다. 기능은 있고, 시연만 생략한다.

### 5.2 어르신 화면

**정상 — 모든 핵심 필드가 `high`**

```
   건강보험료

   청구 금액   3만 2천 원
   납부기한    8월 30일

   ✓ 자녀분께 보냈어요

   [ 🔊 다시 듣기 ]
```
> 🔊 "어르신, 건강보험료 고지서예요. 문서에 적힌 청구 금액은 삼만 이천 원이고,
>    납부기한은 팔월 삼십일입니다. 자녀분께 보내드렸어요."

**금액이 `low` 또는 결손 — 원칙 2 발동**

```
   건강보험료

   금액을 정확히 읽지 못했어요
   자녀분께 확인을 부탁드렸어요

   [ 🔊 다시 듣기 ]
```

**불일치 발견 — 원칙 5 발동**

```
   ⚠  잠깐만요

   이 종이에 적힌 전화번호가
   공식 번호와 다릅니다

   [ 📞 공식 번호로 전화 ]   ← 레지스트리 값
   ✓ 자녀분께 알렸어요
```
> 🔊 "어르신, 잠깐만요. 이 종이에 적힌 전화번호가 진짜 번호와 달라요.
>    여기 적힌 번호로는 전화하지 마세요. 자녀분께 먼저 여쭤보세요."

**어르신 화면에 없는 것:** 계좌번호 · 납부 버튼 · 결제 링크 · 신청 버튼 · 기한 알림.

### 5.3 자녀 화면 — 여기에 모든 행동이 모인다

```
┌─ ⚠ 확인이 필요한 문서 ───────────────────────┐
│  건강보험료 고지서                            │
│  공식 정보 대조 (검사 3건)                    │
│    ✓ 문의전화 — 공식 번호와 일치              │
│    ! 안내 주소 — 공식 도메인과 다름           │
│    — 계좌 진위 — 확인하지 않음                │
│  [ 근거 보기 ]  [ 확인함 ]                    │
├─ 처리할 문서 ────────────────────────────────┤
│  건강보험료   8/30까지   3만 2천 원           │
│  ⓘ 금액 신뢰도 낮음 — [근거 이미지 보기]      │
│  [ 공식 납부 페이지 열기 ]        ← A         │
│  [ 캘린더에 기한 등록 ]           ← B         │
│  [ 확인함 ]  [ 처리 완료 ]                    │
├─ 💡 놓치고 계신 혜택 ────────────────────────┤  ← C
│  기초연금 — 해당되실 수 있습니다              │
│  [ 자격 조건 보기 ]  [ 상담 전화 ]            │
└──────────────────────────────────────────────┘
```

**[처리 완료]를 누르면 어르신 폰에 "자녀분이 처리했어요"가 뜬다.**
상태는 자동으로 넘어가지 않는다. 사람이 누른 결과가 반대편에 반영되어야 진짜 서비스다.

**근거 이미지** — `low` 필드는 `location` 좌표로 **해당 영역만 잘라낸 crop**을 짧은 TTL로 제공한다.
전체 원본이 아니라 금액 부분만. **프라이버시와 검수가 양립하고, `location`이 장식이 아니라 기능이 된다.**

## 6. 아키텍처

### 6.1 전체 흐름

```
[어르신 앱] 촬영
     ▼
[백엔드] POST /v2/files → file_id
         POST /v2/responses (model=agent_id, config_id 고정) → job_id  ※ 즉시 반환
         GET  /v2/responses/{job_id} (include:["all"])  ※ 요청당 1회 조회
     ▼
┌─ Upstage Studio 에이전트 ────────────────────────────┐
│  Parse                                                │
│    └─ Classify ─┬─ 납부   → Extract A                │
│                 ├─ 신청   → Extract B                │
│                 ├─ 안내   → Extract C                │
│                 └─ 기타   → 미매핑 (건너뜀)           │
│                              ↓ 합류                   │
│                     Instruct-1  문서 내부 정합성      │
│                       (Generate and decide)           │
│                              ↓                        │
│                     Instruct-2  쉬운 말 생성          │
│                       (Generate only, 숫자 제외)      │
└───────────────────────────────────────────────────────┘
     ▼
┌─ 안전 게이트 + 검증 계층 (우리 코드) ────────────────┐
│  0. 허용목록 필터 — 저장할 필드만 남기고 나머지 폐기  │
│  R1 발신 정합성  (외부 레지스트리 대조)               │
│  R3 신뢰도 게이트 (high/low)                          │
│  → verdict + 검사 건수 + 근거 목록                    │
│  → 화면·음성 문구를 결정적 템플릿으로 확정            │
└───────────────────────────────────────────────────────┘
     ▼
[DB] 문서 레코드 (pipeline_status / resolution_status 분리)
     ▼
[자녀] 푸시 + A 납부경로 · B 기한등록 · C 숨은혜택
```

> **Instruct-2는 금액·기한 숫자를 생성하지 않는다.** 비수치 설명과 자녀 요약만 만든다.
> 숫자가 들어간 화면·음성 문구는 **검증을 통과한 Extract 값으로 우리가 결정적으로 조립**한다.
> LLM이 만든 문장에 숫자를 맡기면 검증 계층을 우회한다.

### 6.2 Studio 노드 구성

**Studio 노드는 Parse · Classify · Extract · Instruct 네 종류다. Mask는 없다.**
(랜딩 페이지 카드, Key Features 문서의 "the four nodes", Use Cases 예제 4개 모두 일치)

#### Parse — 손촬영 고지서 기준 설정

| 설정 | 값 | 근거 |
|---|---|---|
| **OCR** | **Always** | "scans and photos are mixed in, or recognition quality is disappointing" |
| **Language** | **Korean** | "If the document language is fixed, naming it is more accurate" |
| **DPI** | **300** | "Raise it for documents with small type" — 고지서 깨알 글씨 |
| **Coordinates** | **ON** | "trace or audit where a value came from" — 근거 crop에 필요 |
| Mode | Auto → 부족하면 Advanced | |

품질 개선 공식 순서: ① OCR을 Always → ② Mode를 Advanced → ③ DPI 300 → ④ 더 선명한 원본

#### Classify — 계층형, 행동이 1단계

```
L1 (행동)          L2 (문서 종류)
납부           ─┬─ 건강보험료 / 지방세 / 전기·가스 / 통신
신청·제출      ─┬─ 복지 신청 안내 / 서류 제출 요구
안내           ─┬─ 일반 안내 / 결과 통지
기타(Other)        ← 공식 권고: 반드시 둔다
```

**L1(행동)이 Extract 스키마 분기를 결정하고, L2(문서 종류)가 화면에 표시된다.**
"무엇인지"와 "뭘 해야 하는지"를 Classify 하나로 둘 다 얻는다.

> 공식 권고: "Always add an 'Other' type. Without an escape hatch, the model will force
> documents into an existing type and cause misclassification."

#### Extract — 분기별 스키마 (허용목록 원칙)

```
A. 납부
   발급기관 · 문서명 · 전자납부번호(EPN) · 금액 · 발행일 · 납부기한
   · 문의전화 · 안내URL

B. 신청·제출
   발급기관 · 문서명 · 신청기한 · 필요서류 · 접수처 · 문의전화 · 안내URL

C. 안내
   발급기관 · 문서명 · 요지 · 문의전화 · 안내URL
```

**계좌번호 · 상세주소 · 수신자명은 스키마에서 제외한다.**
Mask 노드가 없으므로 **애초에 추출하지 않는 것이 유일한 확실한 보호**다.
추출한 뒤 가리는 건 `include:["all"]`로 백엔드에 이미 도착한 뒤라 늦다.

**전자납부번호(EPN)를 새로 추가했다** — 이게 A(공식 납부 경로 연결)의 열쇠다.

**Description이 정확도의 최대 레버다** (최대 1,000 bytes, 모델에 보내는 프롬프트).
5가지 용도로 쓴다: 위치 지정 / 포함·제외 / 형식 / 혼동 방지 / 정규화.

> 예 — `납부기한`: "고지서의 '납부기한' 또는 '납기내' 옆 날짜.
> 발행일·고지일·납기후 기한과 혼동하지 말 것. YYYY-MM-DD로 정규화."

#### Instruct-1 — 문서 내부 정합성 (Generate and decide)

`@` 로 상위 Extract 필드를 참조해 문서 **안에서** 확인 가능한 것만 판정한다.

- 분류에 따른 필수 필드 결손 (납부인데 금액 없음)
- 날짜 논리 (`@납부기한` < `@발행일`)
- 결정값: `정상` / `결손` / `날짜이상`

#### Instruct-2 — 쉬운 말 (Generate only)

`#` 로 Instruct-1 결정값을, `@` 로 필드를 참조한다.

| 출력 | 예 |
|---|---|
| 문서 이름 (짧게) | `건강보험료` — 공식 명칭이 아니라 평소 쓰는 말 |
| 설명 문장 (**숫자 제외**) | `건강보험료 고지서예요` |
| 자녀용 요약 | |

**숫자는 우리가 붙인다.** §6.1 참조.

#### 설정 자산을 레포에 커밋한다

Classify 타입과 Extract 스키마는 **Export as JSON** 이 되고 다른 에이전트로 **Import** 된다.
`studio/classify-types.json`, `studio/extract-schema-*.json` 으로 커밋한다.
소스 공개가 규칙이고, **"어떻게 설정했나"에 대한 재현 가능한 증거**가 된다.

### 6.3 응답 파싱 계약 — 구현 전 확정

```
response.output[]
  .model                        "step_1_parse" | "step_2_classify" | ...
  .content[].text               ← 문자열로 직렬화된 JSON. JSON.parse 필요
  .content[].additional_values  ← confidence 등. 별도로 JSON.parse 필요
```

**규칙**

1. **배열 순번 접근 금지.** `output[2]` 같은 코드는 안 된다 — 분기로 단계가 생략될 수 있다.
   반드시 `output[].model` 로 찾는다.
2. `content[].text` 와 `additional_values` 는 **각각 `JSON.parse`** 한다.
3. 필요한 단계가 없으면 **실패 처리**한다. 조용히 넘어가지 않는다.
4. **`config_id` 를 고정한다.** 생략하면 Studio의 **최신** 설정이 호출된다.
   발표 직전 누가 캔버스를 만지면 데모 동작이 바뀐다.
5. 상태값은 **`queued` / `in_progress` / `completed` / `failed`**.
6. **`failed` 는 종결 상태다.** 같은 `job_id` 재조회로는 안 된다 — 새 job을 만든다.

### 6.4 안전 게이트 + 검증 계층

**0. 허용목록 필터 (가장 먼저)**
`include:["all"]` 응답 전체를 DB나 로그에 저장하지 않는다.
§6.2 스키마의 필드만 남기고 나머지는 메모리에서 폐기한다.

**R1 — 발신 정합성** (외부 레지스트리 대조)
- 문서의 `문의전화` ∈ `official_phones` ?
- 문서의 `안내URL` **호스트** ∈ `official_hosts` ?

> URL은 문자열 포함 검사가 아니라 **파싱 후 host 경계 비교**.
> `.go.kr` 전체 허용 금지 — `evil.com/go.kr` 이 통과한다.

> **비교 대상 필드가 `low` 면 R1을 실행하지 않는다.**
> OCR 오독을 공식 불일치로 오판하면 오히려 해롭다. → `review`

**R2는 Studio Instruct-1이 담당한다** (문서 내부 정합성).
단, **`날짜이상`은 `mismatch`가 아니라 `review`** 다 — 체납·재고지 문서에서는 정상일 수 있다.

**R3 — 신뢰도 게이트**
- 핵심 필드(금액·기한·기관)에 `low` 가 있으면 → 숫자를 말하지 않는다 (원칙 2)
- `high` 도 틀릴 수 있다. Upstage 공식 경고: *"confident한데 incorrect한 경우가 있다"*

#### 판정과 표시

| verdict | 화면 |
|---|---|
| `clear` | 확인된 불일치 없음 **(검사 N건 중 N건 일치)** |
| `review` | 확인 필요 |
| `mismatch` | 공식 정보와 다른 항목 발견 |
| `unknown_issuer` | 판단 불가 (등록되지 않은 기관) |
| `not_checkable` | **대조할 연락처를 읽지 못함** |

> **검사 0건인데 `clear`를 주지 않는다.** 연락처가 없는 문서에 "불일치 없음"은 거짓이다.
> 그래서 `not_checkable` 을 신설했다.

**전역 verdict보다 검사 결과 목록이 우선이다.**

```
공식 정보 대조 (검사 3건)
  ✓ 문의전화 — 공식 번호와 일치
  ! 안내 주소 — 공식 도메인과 다름
  — 계좌 진위 — 확인하지 않음
```

무엇을 몇 개 확인했고 무엇을 안 했는지가 보인다. **겸손해 보이는 게 아니라 정밀해 보인다.**

**경고 문구는 LLM이 아니라 결정적 템플릿이다.**
사칭 경고를 Instruct에 맡기면 할루시네이션이 그대로 금전 피해가 된다.

### 6.5 issuer_registry.json

```
issuer_id · aliases[] · official_hosts[] · official_phones[]
source_urls[] · verified_at · coverage_note
```

**초기 대상 4곳** — 국민건강보험공단(fixture ①②) · 보건복지부(fixture ③) ·
한국전력공사 · 국민연금공단.

> 전화번호·도메인 값은 **각 기관 공식 홈페이지에서 직접 확인**해 `source_urls`·`verified_at`에 기록한다.
> **기억이나 추측으로 채우지 않는다.**
> 기관별 검증 문서를 최소 2장 못 구하면 **지원 주장을 2곳으로 줄인다.**

- 코드 `if`문이 아니라 버전 관리되는 데이터 파일
- 출처 URL과 확인일을 **화면에 표시**
- 미등록 기관은 무조건 `unknown_issuer`
- **"전국 공공기관 지원"이 아니라 "4개 기관 시범 적용"**

### 6.6 명시적으로 하지 않는 검증

| 안 하는 것 | 이유 |
|---|---|
| 가상계좌 은행 대조 | **사기 계좌도 같은 은행에 만들 수 있다. 아무것도 증명하지 못한다** |
| QR 디코딩·검증 | Upstage가 QR을 자동 디코딩한다는 보장이 없다 |
| 계좌 명의 조회 / 기관 원장 대조 | 외부 권위 데이터 없음 |

**공식 전화·도메인을 그대로 복사한 사칭 문서는 우리가 탐지하지 못한다.** 이걸 숨기지 않는다.

## 7. 행동 계층 — "이해"에서 "처리"로

> 챌린지 원문: *"build a Document Agent service that goes **beyond understanding documents
> to actually processing them**"*

**전부 자녀 화면에 붙는다** (원칙 1). 어르신에게는 이해와 안심만 남는다.

### A. 공식 납부·신청 경로 연결 — 전자납부번호(EPN)

고지서에는 **전자납부번호 19자리**가 찍혀 있고, 이건 고지서와 납부 화면을 잇는 고유 식별값이다.
인터넷지로(공과금·과태료·국세)와 위택스(지방세)가 이걸로 조회·납부를 받는다.

| | 지금 | DocDo |
|---|---|---|
| 자녀가 부모 공과금을 내려면 | 고지서 사진을 받아서 → 앱 열고 → 메뉴 찾고 → **19자리 직접 입력** | **버튼 하나** |

**동시에 사칭 방어다.** 문서에 적힌 링크가 아니라 **레지스트리의 검증된 공식 경로**로만 보낸다.
`mismatch` / `unknown_issuer` 문서에는 **이 버튼이 아예 뜨지 않는다.**

> 우리가 하는 건 **경로 연결**이지 납부 실행이 아니다. 실제 납부는 공식 사이트에서 본인이 한다.

### B. 기한 등록과 추적

납부기한·신청기한을 **자녀 캘린더에 등록**하고 D-7 / D-3 / D-1에 알린다.
기한이 지나도록 `resolution_status != done` 이면 다시 알린다.

**어르신에게는 기한 알림을 보내지 않는다.** 정작 낼 수 없는 사람에게 마감을 알리면 불안만 만든다.
어르신에게 가는 건 **"자녀분이 처리했어요"** 같은 안심 알림뿐이다.

### C. 숨은 혜택 찾기 — **여기가 이 제품의 핵심 주장**

공공데이터포털에 실제로 있다.

| API | 제공 |
|---|---|
| 한국사회보장정보원 **중앙부처복지서비스** | 목록 + 상세(지원대상·선정기준·신청방법) |
| 한국사회보장정보원 **지자체복지서비스** | 목록 + 상세 |
| 행정안전부 **공공서비스(혜택) 정보 (보조금24)** | 목록 + 상세 |

**우리 문제 정의는 "자격이 있는데 신청하지 않아 못 받는 노인"이다.**
그런데 v1 설계는 **복지 안내문이 우편으로 왔을 때만** 작동했다.
**안내문이 안 와서 못 받는 게 진짜 문제인데 그걸 못 풀고 있었다.**

> 어르신이 **건강보험료 고지서** 한 장을 찍는다
> → 보험료 등급 · 지역 · 연령대를 읽는다
> → 복지서비스 API를 조회한다
> → 자녀 화면: **"기초연금 — 해당되실 수 있습니다"**

**문서 하나를 읽고, 그 문서에 없는 기회를 찾아준다.**

**단정하지 않는다.** "받으실 수 있습니다"가 아니라 **"해당되실 수 있으니 확인해 보세요"**
+ 공식 상담 경로. §6.4 정직성과 일관되게.

**리스크** — 공공데이터포털은 **활용신청**이 필요하다. 개발계정은 대개 자동 승인이지만
일부는 심의에 1~2일 걸린다.
→ **지금 즉시 신청**하고, 승인이 안 나면 **목록을 미리 받아 정적 스냅샷으로 레포에 커밋**한다.
발표에서 "실시간 연동은 승인 대기 중, 현재는 스냅샷"이라고 정직하게 말한다.

## 8. 에러 처리

| 상황 | 처리 |
|---|---|
| job `failed` | **새 job 생성** (기존 `file_id` 재사용, 삭제됐으면 재업로드) |
| 처리 지연 | **P95 실측값**을 기준으로 단일 임계 사용 (v1의 45초/60초 불일치 수정) |
| 앱이 닫힘 | **서버 워커가 완료를 회수한다.** 워커가 없으면 "앱이 열린 동안만"으로 주장을 낮춘다 |
| 네트워크 끊김 | 로컬 큐 + 재시도. **멱등성 키로 중복 job 방지** |
| `other` 분류 | 자녀에게 **알림은 안 보내되 목록에는 남긴다.** 어르신에겐 "버리기 전 확인" (원칙 4) |
| 미등록 기관 | `unknown_issuer` + 자녀 확인 요청. **A 버튼 비활성** |
| 웹에서 카메라 실패 | [사진 파일 선택]을 처음부터 항상 노출 |
| 공개 Demo URL 방문자 | **[합성 샘플로 체험]** — 심사위원이 직접 돌려볼 수 있게 |

**대기 화면에 가짜 진행률을 표시하지 않는다.**

```
업로드 중          "사진을 안전하게 보내고 있어요"
queued/in_progress "문서를 읽고 있어요"
15초 경과          "사진 상태에 따라 조금 더 걸릴 수 있어요"
P95 초과           "분석은 계속돼요. 문서함에서 확인할 수 있어요"
```

## 9. 측정 계획 — 발표에 숫자를 넣으려면 필요하다

### 9.1 규칙 엔진 단위시험 (OCR 무관)

구조화 JSON을 직접 넣어 검사한다: 일치 / 불일치 / 결손 / 미등록 / `low` / 날짜역전 조합.

### 9.2 미사용 문서 E2E 시험

**스키마 튜닝에 쓰지 않은** 익명화 문서 최소 8장, 촬영 조건 3종(정면 / 기울임 / 약한 반사)
→ 16~24회 실행.

### 9.3 발표에 넣을 수치 (전부 `n` 과 함께)

- Classify 정확도 (L1 / L2 각각)
- 핵심 필드 exact match — 발급기관 · 문의전화 · 안내호스트 · 금액 · 기한
- 기대 규칙 판정 vs 실제 결과
- **`high` 인데 틀린 필드 수** ← 이걸 공개하는 게 신뢰를 만든다
- 처리시간 **P50 / P95**

**실측이 없으면 "제품 성능은 아직 검증하지 못했다"고 답한다.** 숫자를 지어내지 않는다.

| # | 문서 | 기대 |
|---|---|---|
| ① | 건강보험료 고지서 **통제본** | `pay` · `clear` (검사 3건 중 3건 일치) |
| ② | **①에서 전화·도메인만 바꾼 변조본** | `pay` · `mismatch` |
| ③ | 복지 신청 안내문 | `apply` · 자녀 [처리 완료] → 어르신 반영 |
| ④ | 미등록 기관 문서 | `unknown_issuer` |

### 10.2 발표 5분 — 라이브는 **1회만**

| 시간 | 내용 |
|---|---|
| 0:00~0:25 | 문제 한 장면. **검증된 통계 하나만** |
| 0:25~0:45 | 라이브 촬영 **시작** (이번 5분에 라이브는 이것뿐) |
| 0:45~1:20 | **실제 Studio 캔버스** — 노드 구성과 type→schema 매핑 |
| **1:20** | **완료 여부를 단 한 번 확인.** 미완료면 즉시 로컬 영상으로 전환 |
| 1:20~2:15 | 결과 + 음성 + **공식 연락처 대조 근거** |
| 2:15~3:00 | **미리 처리한** 통제본·변조본 나란히 비교 |
| 3:00~3:40 | 자녀 화면 — [확인함] → [처리 완료] 실시간 반영 + **C 숨은 혜택** |
| 3:40~4:20 | held-out 정확도 · P50/P95 · 실제 응답 구조 |
| 4:20~4:45 | 제품 가치 + **한계는 한 문장으로** |
| 4:45~5:00 | 전환·지연 버퍼 |

**변조본을 두 번째 라이브 job으로 돌리지 않는다.** 그건 발표를 도박에 거는 것이다.

**폴백 3단계** — ① 라이브 1회 → ② 로컬 저장 30~40초 **무편집** MP4 →
③ job ID · config ID · 단계별 응답이 보이는 정적 스크린샷.

**라이브 경로와 영상 경로를 각각 4분 45초 안에 리허설한다.**

**마지막 30초를 한계 설명에 쓰지 않는다.** 한계는 한 문장으로 끝내고,
마지막은 **"잘못된 번호로 전화하기 전에 멈추게 하고, 자녀 확인까지 닫는다"**로 끝낸다.

### 10.3 Q&A 예상 답변

| 질문 | 답 |
|---|---|
| **"그거 니들이 만든 가짜 문서니까 되는 거 아니냐"** | "맞습니다. ①②는 정확도 자료가 아니라 **두 필드만 바꿨을 때 규칙 결과가 달라지는 통제 실험**입니다. 실제 성능은 튜닝에 쓰지 않은 문서 N장을 여러 촬영 조건에서 별도 측정해 분류·필드·규칙 결과를 나눠 공개했습니다. **공식 연락처를 그대로 복사한 문서는 탐지하지 못합니다.**" |
| 왜 Classify를 행동으로? | 라벨 폭발 방지 + Extract 스키마 분기와 일치. 문서 종류는 L2에서 |
| confidence를 어떻게? | `high`/`low` 범주라 임계값이 아니라 **HITL 플래그**. 공식 권장 패턴 |
| `include`를 왜 `all`? | Instruct가 마지막이라 `last`면 Extract 필드·confidence·location이 사라진다 |
| 개인정보는? | **애초에 추출하지 않는다.** 계좌·주소·이름은 스키마에 없다 |
| 화이트리스트는 하드코딩 아닌가? | 버전 관리 데이터 파일. 출처·확인일·커버리지를 화면 표시. **4개 기관 시범이라 명시** |

## 13. 팀원 백엔드 평가 기준

**기존 코드를 무조건 수용하지 않는다. 우리 계획이 더 나으면 그쪽으로 간다.
단 판단은 아래 기준으로 하고 미리 공유한다.**

### 즉시 교체를 제안하는 경우

| # | 실패 조건 | 대가 |
|---|---|---|
| **H1** | Studio 안 쓰고 v1 API 직접 조합 | **배점 30% 소실** |
| **H2** | API 키가 클라이언트/앱 코드에 | 소스 공개와 결합해 즉시 유출 |
| **H3** | 서버가 job 완료까지 동기 대기 | 배포 후 타임아웃 |
| **H4** | `include:["last"]` | 검증 계층 성립 불가 |
| **H5** | `output[].model` 무시 / `text`·`additional_values` 문자열 JSON 미파싱 | 분기에서 깨짐 |
| **H6** | `config_id` 미고정 | 발표 직전 설정 변경에 노출 |
| **H7** | 앱 종료 후 완료 회수 주체 없는데 백그라운드·푸시 주장 | 거짓 주장 |
| **H8** | 같은 요청 재전송으로 job·알림 중복 생성 | |
| **H9** | 타 household 문서 조회·변경 가능 | |
| **H10** | raw 응답을 로그·DB에 저장 / terminal에서 파일 삭제 미확인 | |
| **H11** | 로컬만 동작. 공개 HTTPS·iPhone·CORS·파일 크기에서 실패 | 제출 불가 |
| **H12** | `low`·결손·미등록인데 숫자 자동 재생 또는 광고 자동 폐기 | **안전 원칙 위반** |

**전체를 버리는 게 아니라 해당 지점만 교체한다.**

### "이미 다 만들었는데" 라고 할 때 — 논쟁 대신 **증거 8개**

- [ ] 배포 URL에서 사진 1장 → 최종 결과 도달
- [ ] 새로고침 후 같은 job 복구
- [ ] raw 응답에 실제 `step_*` 단계 존재
- [ ] 같은 멱등성 키 2회 호출에 job 하나만 생성
- [ ] 타 household 접근이 401/403
- [ ] `failed` 후 새 job 생성
- [ ] terminal 처리 뒤 Upstage 파일 삭제 `deleted:true`
- [ ] 공개 번들·로그에 API 키·PII 없음

**통과한 항목은 유지하고, 실패한 항목만 고친다.**

> **이미 투입한 시간은 품질 근거가 아니다.**

### 판단 원칙

1. 동작하는 코드 > 예쁜 코드
2. 교체 제안 시 **"무엇이 왜 문제인지 + 대안 + 소요 시간"**을 함께 말한다
3. 점수에 직결되지 않는 차이는 그냥 수용한다

## 14. 착수 순서

### 1순위 — Studio kill-test (앱 코드 작성 전)

Mask 없이 `Parse → Classify → 타입별 Extract → Instruct` 를 만들고 **납부·신청·기타 각 1장**을 돌린다.

**확보해야 할 것:** raw `include:["all"]` 응답 · 분기가 실제로 갈리는지 · 실제 처리시간 · `config_id`

**이걸 확보하기 전에 앱 UI를 만들지 않는다.**

### 2순위 — 팀원 백엔드를 H1~H12로 실행 평가

설명을 듣는 게 아니라 **코드를 열고 배포 환경에서 golden path를 돌린다.**

### 3순위 — E2E 하나 고정 → **백업 영상 먼저**

`iPhone 촬영 → Studio → 안전 게이트 → 어르신 화면 → 자녀 상태 변경` 하나를 안정화하고
**바로 영상을 찍는다.** 그 뒤에만 푸시와 UI 장식을 추가한다.

### 일정

| 언제 | 목표 |
|---|---|
| ~ 자정 | **kill-test 완료 + 사진 1장이 결과가 되는 길** |
| 자정 ~ 새벽 | 안전 게이트 · 검증 계층 · 두 화면 · 음성 |
| 새벽 ~ 아침 | fixture 4장 · **§9 측정** · A/B/C |
| 08:00 ~ 11:00 | **백업 영상** · 발표자료 · README · Description 재작성 |
| **11:00 ~ 12:00** | **제출** (11시에 일단 다 채우고 남은 1시간은 다듬기) |
| 13:00 | 발표 |
